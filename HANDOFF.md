## 1. Data layer essentials (read before touching schema or queries)

- Contract-first ORM at `src/prisma/contract.prisma`. Workflow: edit the `.prisma` file → `npx prisma contract emit` → `npx prisma db update --db "$DATABASE_URL" --dry-run --json` to preview → apply with `npx prisma db update --db "$DATABASE_URL" --advance-ref db -y` (only add `--confirm postgres` if the dry-run shows destructive ops). `$DATABASE_URL` is **not** exported by default in a fresh shell — load it first: `set -a; source .env 2>/dev/null; source .env.local 2>/dev/null; set +a;` then run the prisma command in the *same* shell invocation (env vars don't persist between separate Bash tool calls in this environment).
- Query pattern everywhere: `db.orm.public.ModelName.where({...}).all()` / `.first()` / `.create()` / `.update()` / `.delete()`. **No `{in:[...]}` operator** — fetch broad and `.filter()` in JS, or loop per-id.
- `.update()` convention: `undefined` in the input object means "leave field alone"; you must pass explicit `null` to clear a field. Every write action in this codebase builds a `data: Record<string, unknown> = {}` object and only sets keys that are `!== undefined`.
- No native `Json` or `Bytes` column type is used anywhere in this contract (confirmed via the prisma-8 skill and by grepping the whole schema) — flexible/structured data is stored as a `String` column holding `JSON.stringify(...)`, parsed on read. Binary files (images) are stored as **base64 text** in a `String` column, not a blob type. Follow this precedent, don't introduce `Bytes`/`Json` as a "cleaner" alternative without checking it's actually supported first.
- Every write server action returns `{success: true, ...}` or `{error: string}` and wraps its body in try/catch, logging via `console.error`.
- Every action that returns data to a client component does `JSON.parse(JSON.stringify(result))` before returning, to strip Temporal/Date objects that can't cross the server/client boundary.
- DateTime fields go through two local helpers defined at the top of each actions file: `toInstant(date: Date)` (→ `Temporal.Instant`) and `epochMs(instant)` (→ number). Copy these into any new actions file that needs DateTime writes — don't import them cross-file, the convention is to redefine locally (see `lib/actions/microsite.ts` for the minimal version, `lib/actions/school.ts` for the full version with `startOfDay` too).
- **Standalone `tsx` scripts that import anything from `lib/actions/school.ts` will crash** with `TypeError: GoogleProvider is not a function` — that file transitively imports `next-auth`'s `authOptions` for session-gating, which only resolves correctly inside Next's own bundler. Any throwaway verification script must call `db.orm.public.X` directly, never import from `lib/actions/*`. Verify actual server actions via the live dev server (curl + cookie jar, or browser automation), not standalone scripts.
- RBAC: `requireOrgRole('SCHOOL', [roles])` / `requireOrgAccess(orgType | orgType[])` from `lib/rbac.ts` gate Admin/Teacher-style pages (redirect to `/` on failure — no error page, just silent redirect, this is by design not a bug). Parent/Student self-service portals are **not** `OrganizationMember`s, so they session-gate manually inside the action via `getServerSession(authOptions)` + email lookup (see `getParentPortalData()` / `getStudentPortalData()` in `lib/actions/school.ts`).

## 2. Dev server / environment quirks

- Port **3001**, not 3000 (3000 is occupied by an unrelated project on this machine). Start with: `PORT=3001 nohup npm run dev > /tmp/some.log 2>&1 & disown`, then poll `curl -o /dev/null -w "%{http_code}" http://localhost:3001/` until it returns 200 (can take 15-20s cold).
- The dev server periodically goes unresponsive after heavy use, or throws `CONTRACT.MARKER_READ_FAILED` / stale-connection errors after sitting idle. Fix: find the PID (`Get-CimInstance Win32_Process -Filter "CommandLine like '%next%dev%'"` via PowerShell, or `ps`), `taskkill //F //PID <pid> //T`, `rm -rf .next`, relaunch as above.
- Demo login: every seeded user has password `1234` via a dev-only NextAuth Credentials provider with **id `"demo"`** — the login POST must go to `/api/auth/callback/demo`, **not** `/api/auth/callback/credentials`. From a browser tab already on the target origin, the reliable way to log in via automation is `fetch`-based (not clicking the real form, which has been flaky in this session's browser-automation tool):
  ```js
  const csrfRes = await fetch('/api/auth/csrf', { credentials: 'include' });
  const { csrfToken } = await csrfRes.json();
  const body = new URLSearchParams({ email: '<user>@cityconnect.local', password: '1234', csrfToken, callbackUrl: '/<target>', json: 'true' });
  await fetch('/api/auth/callback/demo', { method: 'POST', credentials: 'include', headers: { 'Content-Type': 'application/x-www-form-urlencoded' }, body });
  ```
  Key seeded accounts (all password `1234`): `principal@cityconnect.local` (School ADMIN), `admin@cityconnect.local` (a shared multi-vertical demo account — also holds School TEACHER membership, is the class/form teacher used in promotion-tool testing), `student@cityconnect.local` (linked to student1/Alex Johnson), `parent1@cityconnect.local` (linked to Alex Johnson), `parent2@cityconnect.local` (linked to Zoe Smith/student2).
- Browser automation tool notes (if your environment has an equivalent): coordinate-based clicks are unreliable in this session (viewport/DPI scaling mismatch caused repeated mis-clicks) — prefer `find` (natural-language element lookup) + ref-based clicks over raw coordinates. Never trigger a `confirm()`/`alert()` dialog via a real click (it can hang the tab); if a flow requires confirming a destructive action, verify the underlying write logic via an isolated throwaway-row DB script instead.

### 3.7 Microsite / Website Builder — cross-vertical, THE ACTIVE TASK, interrupted mid-verification

**This is genuinely finished and live-verified working**, with one last housekeeping step left incomplete (see "Exact stopping point" below) — this is not a half-built feature, don't be afraid to build on it.

**What it is**: any organization (not just schools — School was just the first one wired up end-to-end, per explicit user instruction "we would test it with school") can build one dedicated, professional single-page marketing website, independent of and additional to how they already show up in-app (Explore/local listings are untouched). Modeled on Shopify's Online Store 2.0 approach (a theme + an ordered list of typed sections edited via forms), not a freeform drag-and-drop canvas — deliberately, to match this codebase's existing list+modal admin-UI conventions and minimize engineering risk.

**Explicit scope decisions the user made** (do not second-guess these without asking):
- Billing/paid-plan gating: **out of scope for now**. Every org gets full builder access. When billing is built later, it should gate behind a single entitlement flag on the org — nothing in the builder itself needs to change for that.
- Domains: **subdomain now** (`<slug>.<apex domain>`), **custom domain later** (explicitly deferred, not started).
- Asset hosting: **self-hosted by us**, not a third-party object store (no S3/Cloudinary integration — deliberately, per user instruction "asset hosting would be done by us"). Implemented as base64-in-Postgres (see the `Asset` model) since no `Bytes` scalar type is confirmed-supported in this contract dialect (see §1) and this was the safe, zero-new-infra choice.
- Scope boundary: this does **not** touch Explore or any per-vertical listing surface — it's a genuinely separate, additional thing.

**Schema** (`src/prisma/contract.prisma`, new section "MICROSITE BUILDER" right after "ORGANIZATIONS & RBAC" and before "CITYPAY" — migration already applied, all 10 operations were purely additive, verified via dry-run before apply):
- `Microsite` — 1:1 with `Organization` (`organizationId` unique), `slug` (unique, subdomain-ready), `title`, `tagline`, `theme` (string key into a static theme config, default `"minimal"`), `status` (`"draft"` | `"published"`), SEO fields, `logoAssetId`/`faviconAssetId` (loose string refs to `Asset.id`, not FK-constrained), `publishedAt`.
- `MicrositeSection` — belongs to a `Microsite`, `type` (string: `hero`/`about`/`services`/`gallery`/`hours`/`testimonials`/`contact`/`cta`/`footer`), `order` (int, reorderable), `visible` (bool), `content` (JSON-stringified, shape depends on `type` — see `DEFAULT_CONTENT` in `components/microsite/MicrositeBuilder.tsx` for the exact shape of each type).
- `Asset` — self-hosted image storage: `organizationId`, `fileName`, `mimeType`, `size`, `data` (base64 `String`). 5MB cap enforced in `uploadAsset()`.
- `Organization` got two new back-relations: `microsite Microsite?` and `assets Asset[]`.

**Actions** — new file `lib/actions/microsite.ts` (cross-vertical, deliberately not added to `lib/actions/school.ts`): `getMicrosite`/`getMicrositeBySlug`(public, published-only)/`isSlugAvailable`/`createMicrosite`/`updateMicrositeSettings`/`publishMicrosite`(refuses to publish with zero visible sections)/`unpublishMicrosite`/`addMicrositeSection`/`updateMicrositeSection`/`deleteMicrositeSection`/`reorderMicrositeSections`/`uploadAsset`/`deleteAsset`.

**UI**:
- `components/microsite/themes.ts` — `THEMES` config (4 curated presets: `minimal`, `bold`, `warm`, `editorial` — each just a set of CSS-variable-ish tokens: bg/surface/text/textMuted/accent/accentText/headingFont/bodyFont/radius, no Google Fonts dependency, web-safe stacks only) + `SECTION_TYPES` + `DEFAULT_THEME`.
- `components/microsite/MicrositeRenderer.tsx` — the **public-facing** renderer, a pure server component, switches on section `type`, applies theme via inline styles (not Tailwind dynamic classes, deliberately, since Tailwind JIT can't safelist truly dynamic class names).
- `components/microsite/MicrositeBuilder.tsx` — the **admin-facing** builder: create-site form (if none exists yet), section list with reorder/visibility-toggle/edit/delete, "Add Section" type picker, a generic `SectionEditorModal` that dispatches to a per-type form (`SectionForm` switch), a shared `ListEditor` for repeatable sub-items (services list, hours rows, testimonials, social links), `AssetPicker`/`GalleryPicker` (client-side `FileReader` → base64 → `uploadAsset`), Settings & Theme tab (theme swatches, logo, title/tagline/slug/SEO).

**Routes**:
- `app/site/[slug]/page.tsx` — public rendering route, **intentionally placed outside every route group** (not under `(resident)` or `(admin)`) so it inherits only the bare root layout (`app/layout.tsx`) with zero app chrome — verified this renders clean with no sidebar/nav bleeding through. Calls `getMicrositeBySlug`, `notFound()` if missing/unpublished. Has `generateMetadata` wired to the site's SEO fields.
- `app/api/assets/[id]/route.ts` — **the first non-NextAuth route under `app/api/*` in this codebase** (flagged explicitly since `CLAUDE.md` says "there is effectively no `app/api/*` surface besides NextAuth" — that statement is now slightly stale, update it if you touch that file). Decodes the base64 `Asset.data` back to a `Buffer` and streams it with the right `Content-Type` + long `Cache-Control`.
- `app/business/website/page.tsx` — the cross-vertical **admin** route, deliberately **not** nested under any vertical's `(admin)` route group (since the feature isn't vertical-specific). Reached via `?org=<organizationId>` query param; gates access by checking the signed-in user has a membership in that exact org with role `OWNER`/`MANAGER`/`ADMIN` (redirects to `/` otherwise). Entry point wired from the School admin sidebar: a new "Business" section at the bottom of `components/school/AdminDashboard.tsx`'s sidebar with a "Website" link to `/business/website?org=${organizationId}` — **other verticals' dashboards do not have this link yet** — that's the natural next step if extending to another vertical (Hotel, Restaurant, etc.), see "Suggested next steps" below.

**Subdomain middleware** (`middleware.ts` — **rewritten, high blast-radius change, extra scrutiny warranted, already tested**): the old file was just `export { default } from "next-auth/middleware"` with a static `matcher` list of protected path prefixes. It's now a real middleware function that (1) checks the `Host` header for a `<slug>.<APEX_DOMAIN>` pattern (env var `NEXT_PUBLIC_APEX_DOMAIN`, defaults to `"localhost"` — modern browsers resolve `*.localhost` to `127.0.0.1` automatically, so this works in local dev with zero `/etc/hosts` changes) and rewrites to `/site/<slug>` if so — public, no auth; (2) otherwise, for the same `PROTECTED_PREFIXES` list as before, calls `withAuth(req as any)` (the actual `next-auth/middleware` function, imported and invoked directly — **not reimplemented**, chosen deliberately to byte-for-byte preserve the exact prior redirect behavior rather than risk subtly changing it) and returns its result if it redirects. The `matcher` had to widen from the old specific-prefix list to `["/((?!_next/static|_next/image|favicon.ico).*)"]` so the subdomain check can run on *any* path (including `/`) — this was necessary and is safe (verified below), but is the single biggest-blast-radius change in this whole session.
  - **Verified via curl** (not yet re-verified after the interrupted final check, but was passing before the interruption): unauthenticated `/school/admin` and `/hotel/manager` still `307` redirect to `/api/auth/signin?callbackUrl=...` exactly as before; `/school/student` (intentionally unprotected) still returns `200` with no auth; `/site/lincoln-high` returns `200` publicly; a spoofed `Host: lincoln-high.localhost:3001` header on `/` correctly rewrites and serves the microsite; an unknown slug (via path or subdomain) correctly `404`s.

**Seed data**: `scripts/seed.ts` gained a block (right before the final `console.log('Database seeded successfully!')`) creating a published `Microsite` for the school org — slug `lincoln-high`, theme `editorial`, 6 sections (hero/about/services/hours/contact/footer) with real placeholder copy.
